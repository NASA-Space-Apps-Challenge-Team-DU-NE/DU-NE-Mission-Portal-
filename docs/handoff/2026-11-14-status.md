# LUNA-NAV 진행 현황 (2026-11-14, 버그 수정 후)

기준: 실제 Drive 데이터(`DU_NE Data`, 1,727개 파일 · 9.1 GB)로 파이프라인 s00–s90을 한 번 끝까지 돌렸다.
그 검증에서 나온 버그 5개(+1개)를 고쳤다. **팀원 PC에서 s30·s50·s60·s80·s90을 다시 돌리면 산출물이 바로잡힌다** (4절 명령).

## 1. 완성된 것

### 문서·저장소
- `CLAUDE.md` v4, `docs/ARCHITECTURE.md`, `TASKS.md`, `docs/decisions.md`, `docs/sources.md`, `docs/validation.md`, `docs/coordinates.md`
- GitHub 저장소에 커밋되어 있고 CI 워크플로가 있다.
- Vercel 배포는 당분간 제외 (팀 합의).

### 웹앱 (`web/`)
- React + Vite + three.js + Zustand. 10개 페이지와 오른쪽 3D 달·현장 뷰 화면이 모두 있다.
- core 계산 (Vitest 41개 통과)
  - 천체력 보간·근사, 지평선, 하늘, 타임라인, 이벤트
  - 격자 점수, 시나리오·대안, 참고 사례
  - 에너지·전력, 지상국, 위험, 검증 통계, 내보내기
- Worker 3개: 격자, 역방향 탐색, 시뮬레이션
- 화면 보강
  - 2D 지도·3D 남극에 Moon Trek 실제 표면 배경
  - 3D 달에 태양·지구 표시
  - 07 통신 페이지에 KPI·그래프·교신 창·지상국 표
  - 파노라마·하늘 돔에 달 표면 질감
- 데이터가 없으면 "자료 없음"을 표시한다. 격자가 없으면 "근사 격자 · 지형 미반영" 배지를 단다.

### 파이프라인 (`pipeline/`)
- s00–s90 10단계를 실제 데이터로 실행했다. **pytest 29개 통과** (이번에 5개 추가).
- 실제 Drive 형식에 맞춰 고친 것
  - 엑셀 헤더 위치
  - PDS 중첩 IMAGE 객체, m/pixel 배율
  - 한국어 카테고리·라벨
  - 미션 CSV 열 이름
  - 칸 경계(bin) 형식 성분 표
  - DSN 좌표·마스크 열
  - Horizons 좌표계 헤더
  - s40 폴더 생성
- 좌표계 확인 (`docs/coordinates.md`)
  - LOLA = MEAN EARTH/POLAR AXIS OF DE421, Horizons = MOON_ME
  - PGDA69 GeoTIFF도 메타데이터에 "MEAN EARTH/POLAR AXIS OF DE421"
  - 극평사 픽셀 규칙은 실제 고도(Shackleton 바닥 −2.78 km 등)로 확인

## 2. 이번에 고친 버그

| # | 증상 | 원인 | 수정 | 결과 (개발 PC에서 미리 확인) |
| --- | --- | --- | --- | --- |
| 1 | 일조율 vs PGDA69 RMSE 84 | PGDA69 GeoTIFF는 int16 + 밴드 배율(4e-5)인데 배율을 안 곱함. 대신 블록마다 "퍼센트겠지" 추측 | `io/geotiff.py` `band_scale`로 배율·오프셋 적용. 비율이 0–1 밖이면 멈춤 | 85°S 이남 대조 RMSE 약 0.066 (6.6%p), r 약 0.90 |
| 2 | WAC 조명률 값 약 1e36 | PDS 실수 결측값(−3.4e38)이 평균에 섞임 | 결측 처리, 라벨대로 % → 0–1 | 원본 0–71.6 % 범위 확인 |
| 3 | Shackleton 마스크 Drive 대비 RMS 5.47° | 대표 좌표가 30 m DEM의 작은 구덩이(주변보다 5–8 m 낮음) 안에 떨어짐 | 관측점 150 m 안은 지평선 계산에서 빼고, 지면 고도는 반경 150 m 평균 (PROVISIONAL) | 같은 계산 재현 RMS 약 0.37° |
| 4 | 천체력 검증 0행 | 기준 CSV 첫 줄이 `#` 주석 | `comment="#"`, 관측점은 머리줄 좌표 사용 | 12개 표 모두 각거리 최대 0.006° 이하 (허용 0.1°) |
| 5 | PA→ME 검증 0행 | SPICE tf의 MOON_ME가 단위행렬 별칭 | 별칭을 따라 실제 회전 프레임을 읽음 | 회전 0.0289° (표면 약 875 m) |
| + | 하늘 입체각 `sky_sr`가 음수 | 1번과 같은 원인 (배율 2e-4 + 6.2832) | 1번 수정에 포함 | s50 재실행 후 확인 |

- 3번의 150 m 값은 임시값이다. `docs/decisions.md`에 적었고 팀 확인이 필요하다.
- 1번 결과는 개발 PC에서 근사 대조한 값이다. 팀원 PC에서 s50·s80을 다시 돌려야 확정된다.

## 3. 미완성 · 필요한 것

### 3.1 다시 돌려야 하는 것
- s30(마스크) → s50(레이어) → s60(텍스처) → s80(검증) → s90(manifest). 4절 명령.
- 다시 돌린 뒤 10 검증 페이지에서 확인할 것
  - 일조율 RMSE가 0.1 아래인지
  - Shackleton 마스크 RMS가 1° 아래인지

### 3.2 데이터·자료 부족
| 항목 | 상태 | 필요한 것 |
| --- | --- | --- |
| spiceypy | 설치 안 함 (선택) | PA→ME 방향을 SPICE로 직접 대조하려면 `pip install spiceypy` |
| 여주 지상국 | 안테나 좌표 없음 → 교신 창에서 빠짐 | 출처 있는 좌표·최소 고도각 (KARI 공개 자료 등) |
| 착륙선 프리셋 | 근사값 4종, 제원 CSV와 대조 안 함 (TASKS P09) | `LUNA_LANDER_TECHNICAL_SPECS.csv` 대조 |
| 5 m 국지 지형 | 사용 안 함 | 팀 결정 D7. P1-05 완성, P3-05 착륙 오차가 여기에 걸림 |
| 아르테미스 후보 | 목록 기준 미정 | 팀 결정 D2 |
| 중성자·온도 보조 레이어 | 안 만듦 (선택) | D4에서 물 지표로 쓰기로 하면 추가 |
| 착륙지 대표 좌표 | 대부분 `verified: false` ("대표 지점 근사값") | 출처 대조. 3번 버그처럼 좌표가 조금만 달라도 마스크가 바뀐다 |

## 4. 실행 명령 (Windows cmd)

### 4.1 파이썬 테스트와 파이프라인 재실행
```bat
cd C:\Users\USER\Desktop\project\LUNA-NAV\pipeline
.venv\Scripts\activate
pytest
python -m luna s30 --force
python -m luna s50 --force
python -m luna s60 --force
python -m luna s80 --force
python -m luna s90 --force
```
- `pytest` 결과는 `29 passed`가 나와야 한다.
- s30이 끝나면 착륙지마다 "Drive 대조 RMS"가 찍힌다. shackleton_rim이 1° 아래인지 본다.
- 검증 숫자는 `docs\validation.md`의 "자동 결과 (s80)" 표에 다시 써진다.

### 4.2 웹 확인
```bat
cd C:\Users\USER\Desktop\project\LUNA-NAV\web
npm run check
npm run dev
```
- 브라우저에서 http://localhost:5173 을 열고 10 검증 페이지를 본다.

## 5. 실행 환경 메모
- Python은 **3.13**을 쓴다 (3.11 미설치). `py -3.13 -m venv .venv`
- 데이터 경로는 `.env.local`의 `LUNA_DATA_DIR`에 적는다 (커밋 안 됨).
- `*.egg-info/`는 `.gitignore`에 있다.
