# 데이터 수정 원칙 (필독)

**이 폴더의 파일을 고치거나 새 파일을 올리기 전에 이 문서를 끝까지 읽는다.**
여러 사람이 같은 폴더를 쓰기 때문에, 아래 원칙을 지키지 않으면 다른 사람의 수정이 말없이 덮어써진다.

작성 2026-11-13. 원칙을 바꾸려면 팀에 먼저 알리고, 바꾼 내용을 `01_변경_기록.md`에 남긴다.

## 1. 한 줄 요약

1. 고치기 전에 `01_변경_기록.md`를 보고, 지금 그 파일을 누가 고치고 있는지 확인한다.
2. 고치기 시작할 때 `01_변경_기록.md`에 "작업 중"을 적고, 끝나면 "완료"로 바꾼다.
3. `Raw_Data/`의 원자료는 고치지도 지우지도 않는다.
4. 지우지 말고 `_Archive/`로 옮긴다.
5. `파일 (1).json`처럼 번호가 붙은 사본이 생기면 바로 합치고 사본을 지운다.

## 2. 왜 충돌이 생기나

- Google Drive는 같은 파일을 두 사람이 동시에 고치면 한쪽을 `이름 (1).확장자` 사본으로 따로 만든다. 사본을 아무도 보지 않으면 한 사람의 수정이 사라진 것처럼 된다.
- 코드 저장소의 `pipeline/drive.py push`나 직접 복사로 로컬 파일을 올리면, 그 사이에 다른 사람이 드라이브에서 고친 내용을 덮어쓸 수 있다.
- 드라이브 웹 화면에서 같은 이름의 파일을 업로드하면 기존 파일이 새 버전으로 바뀐다. 이전 버전은 "버전 관리"에서만 보인다.

## 3. 폴더별 규칙

| 폴더 | 누가 바꾸나 | 규칙 |
| --- | --- | --- |
| `Raw_Data/` | 아무도 고치지 않는다 | 외부에서 받은 원본 그대로 둔다. 새 원자료는 하위 폴더를 새로 만들어 추가하고(예: `Raw_Data/LOLA_DEM_20m/`), 출처 URL과 받은 날짜를 `README.md` 표에 적는다 |
| `Catalogs/` | 손으로 고치는 파일 | 한 번에 한 사람만 고친다. 시작 전에 `01_변경_기록.md`에 작업 중 표시. JSON 형식과 필드 이름은 바꾸지 않는다(바꿔야 하면 팀 합의 후) |
| `Horizon_Masks/`, `Web_Derived/` | 스크립트가 만드는 파일 | 손으로 고치지 않는다. `pipeline/build_all.py`, `pipeline/horizons_table.py`로 다시 만들어 올린다 |
| `Reference_Tables/` | 스크립트가 만드는 파일 | 기존 파일을 덮어쓰지 않는다. 조건이 다르면 파일 이름에 위치·날짜를 넣어 새로 만든다 |
| `Workspace/<이름>/` | 각자 | 개인 작업 공간. 다른 사람의 폴더는 건드리지 않는다. 공용 폴더로 옮길 때 3절 규칙을 따른다 |
| `Incoming/` | 누구나 | 어디에 둘지 정하지 못한 새 데이터를 일단 여기에 둔다. 출처가 없는 파일은 공용 폴더로 옮기지 않는다 |
| `_Archive/` | 누구나 | 지울 파일은 여기로 옮긴다. `_Archive/<날짜>_<원래 폴더>/` 형식 |

## 4. 수정 절차

1. `01_변경_기록.md`에서 같은 파일에 "작업 중"인 줄이 있는지 본다. 있으면 그 사람에게 먼저 묻는다.
2. 아래 형식으로 한 줄 추가한다: 상태는 `작업 중`.
3. 파일을 고친다. 오래 걸리면 고친 사본을 `Workspace/<이름>/`에서 만든 뒤, 마지막에 한 번만 공용 파일에 반영한다.
4. 반영 직전에 공용 파일의 수정 시각이 1번 때와 같은지 다시 본다. 달라졌으면 그 변경을 먼저 합친다.
5. 기록의 상태를 `완료`로 바꾸고 바뀐 내용을 한 줄로 적는다.

## 5. 새 데이터 추가 절차

1. 들어갈 폴더를 3절 표에서 고른다. 맞는 곳이 없으면 `Incoming/`.
2. 파일 이름에 무엇인지 알 수 있는 이름을 쓴다. 공백 대신 `_`를 쓰고, 날짜는 `YYYY-MM-DD`.
3. `README.md`의 폴더 표에 출처 URL, 받은 날짜 또는 만든 스크립트, 검증 여부를 적는다.
4. 확인하지 못한 값이 든 데이터는 항목에 `verified: false`를 달거나 README에 "미검증"이라고 적는다.
5. `01_변경_기록.md`에 한 줄 남긴다.

## 6. 코드 저장소에서 `pipeline/drive.py`를 쓸 때

- `python pipeline/drive.py status`로 먼저 차이를 본다.
- `push`는 마지막 동기화 이후 드라이브 쪽이 바뀐 파일을 덮어쓰지 않고 건너뛴다. 이때는 `pull`을 먼저 한다.
- `pull`은 아직 올리지 않은 로컬 수정이 있는 파일을 덮어쓰지 않는다.
- 양쪽이 모두 바뀐 파일이 있으면 아무것도 옮기지 않고 멈춘다. 내용을 직접 합친 뒤 다시 실행한다.
- `--force`는 한쪽을 버려도 된다고 확인했을 때만 쓰고, 쓴 사실을 `01_변경_기록.md`에 적는다.
- 이 검사는 스크립트를 쓴 사람에게만 적용된다. 드라이브에서 직접 고치는 사람은 4절 절차를 따른다.

## 7. 사고가 났을 때

- 덮어쓴 파일은 드라이브 웹 화면에서 파일을 우클릭 → 파일 정보 → 버전 관리에서 이전 버전을 되살린다(일정 기간만 보관된다).
- 번호가 붙은 사본(`이름 (1).json`)은 두 파일을 비교해 합치고, 사본은 `_Archive/`로 옮긴다.
- 무엇을 되살렸는지 `01_변경_기록.md`에 적는다.
